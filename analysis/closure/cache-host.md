## U13 main question

Verdict: CLOSED for "no prefill redo on cached positions". PARTIAL on the wording "decode kernels": the uncached suffix of a resumed prompt goes through the prefill path (QKV + RoPE for the NEW positions only), and only generated tokens go through decode.

Answer in plain words: on a hit the engine restores the O(1) recurrent state of the entry, keeps (or copies as raw rows) the existing KV pool rows, and starts the prefill loop at the first uncached token. The forward call receives only tokens [resume, n). Positions below `resume` are never fed to the model again, so their QKV and RoPE are not recomputed. Their K/V rows are read from the pool as stored (kernel side: analysis/kernels-attention.md section 8).

Evidence:

1. Lookup returns a resume position and the request starts there.
   - `0187fb00.c` (prompt_cache_try_restore): `iVar6 = *(int *)(lVar14 + 0x48)` (matched token count, ~line 96) and the function returns `iVar6` (end of file).
   - `01860720.c:51-53`: `uVar1 = FUN_0187fb00(param_2,param_3,param_4); *(undefined4 *)((long)param_1 + 0x24) = uVar1; *(undefined4 *)(param_1 + 4) = uVar1;` The plan struct's "tokens done" field starts at the cache hit length.
2. The prefill driver consumes from that position only.
   - `018680b0.c` (FUN_018680b0, one prefill step), near the middle: `FUN_01905ae0(*(undefined8 *)(param_1 + 0x60),(long)iVar7 * 4 + *param_2,iVar21);` with `iVar7 = (int)param_2[4]` (done count, initialised from the hit) and `iVar21` the piece length. That is (model, token_ptr + done*4, count).
   - `018680b0.c:24-37`: `if (iVar21 <= iVar7) { ... }` with return value 1: when done >= prompt length (full-prompt hit) the step returns "finished" without any forward call.
   - Non-cache path for comparison, `01846b20.c:156-161`: the same call `FUN_01905ae0(*param_1,(long)(int)param_2[0x82] * 4 + param_2[7],pFVar17)`, where `param_2[0x82]` is the done count.
   - `01846b20.c:136-148`: logs `"flash_serve: req %ld prefill %d/%d tokens, 0.0 s%s\n"` with `iVar21` = done count at start and the suffix `" (the prompt cache's hit)"` when `0 < iVar21`. The start offset equals the hit.
3. KV rows are not recomputed in either in-place mode.
   - In place (`HALOGEN_CACHE_INPLACE=1`, on per run log line 55): `0187fb00.c:70-80`: if the entry's KV rows are on a different slot than this request, it prints `"prompt cache: the entry's KV rows are on slot %d and this request is on slot %d; it runs cold (HALOGEN_CACHE_INPLACE=0 copies the rows instead)"` and returns 0 (no hit). So an in-place hit only happens when the rows are already where the request runs.
   - Pool mode (`*(char*)(lVar7+0xcd)==1`): `0187fb00.c:55-65`: if the entry's region differs from the request's region, `FUN_01901c50` (kv_copy_region, function-map line 943) copies rows region to region (counter text `"%ld hits copied their rows across regions"`, `0182ba00.c:1168`); otherwise nothing moves. A copy is a memory copy of rows, not a recompute (inferred from the name and from the absence of any model call in the caller; body of 01901c50 not read).
   - Entry content: `018fe4f0.c` (snapshot walker, loop over 0x30 = 48 layers). When the in-place flag `param_3` is 0 it also snapshots K and V slabs (`n_pos << 10` bytes each); when 1 it skips them. Layers with `layer % 4 == 3` (test `(~uVar6 & 3) == 0`) are the KV layers; the other 36 layers save DeltaNet state 0x300000 B (3 MiB) and conv state 0x14000 B (80 KiB) each (`local_70 = 0x300000`, `local_70 = 0x14000`). 36 x (3 MiB + 80 KiB) = 110.8 MiB, matching the banner's "111 MiB each" (arithmetic on decompiled constants, computed here).
4. On failure: `"prompt cache: snapshot load failed; this request runs cold and the entry is dropped"`.
5. Plan fields beyond the hit: `01860720.c:60-76` copies saved `vector<float>` and several sub-vectors from the entry (+0xa0, +0xc8 ... +0x148) into the plan when the entry is a full-prompt entry. Inferred: these are the saved last-position sampler inputs (logits), which is why a full-prompt hit needs no forward call.

## Cache modes and entry kinds

Mode 1 prints "bitwise resume (%d entries, chunk %d, %.0f MiB each at ctx %d)"; mode 2 prints "resume-anywhere ... NOT bitwise" (both strings in the binary). `0182ba00.c:835` confirms composable context needs `HALOGEN_PROMPT_CACHE=2`. The 1/2 to banner mapping is inferred from the `mode < 2` branches in 01860720.c and 018680b0.c described below.
- Entry kinds (`0186cdc0.c:20-36`, cache_entry_kind_name): flag +0x88 "a full entry", +0x89 "a tail checkpoint", +0x8a "a system-prompt anchor" (+0x8b set: "a shared system-prompt anchor"); anything else falls to a branch/leaf lookup.
- Entry cap (`01852ca0.c:128-140`): `((BRANCHES << SNAP3) + FULL + 1) * slots`, overridden by `HALOGEN_CACHE_ENTRIES` (warning when below that). Banner value here: 24.
- Env knobs read in the constructor (`01852ca0.c:71-110`): `HALOGEN_CACHE_INPLACE` (+0xd9), `HALOGEN_CACHE_FULL` (+0xa0), `HALOGEN_CACHE_DISK_DEEPEN` (+0xa2), `HALOGEN_CACHE_SNAP3` (+0xa1), `HALOGEN_CACHE_CKPT` (+0xa3), `HALOGEN_CACHE_EVICT` (=0 gives plain LRU), `HALOGEN_CACHE_BRANCHES`, `HALOGEN_CACHE_ENTRIES`, `HALOGEN_CACHE_FILE` (single snapshot file with an O_DIRECT fd at +0xb4; forces entries to 1).
- SNAP, SNAP2, SNAP3: three snapshot positions per prefill piece in `018680b0.c:~120-262` (`local_48` low, `local_48` high, `local_40`), stored with kind argument 0, 1, 2 to `FUN_0186a470` (`018680b0.c`, three blocks gated by byte flags at `model+0x4c8`, `+0x4c9`, `+0x4ca`). - `cache_insert_new_entry` is `0186b270.c` (626 B, string "a new entry"), called as `FUN_0186b270(param_1,0xffffffff,0)` from `0186a470.c:191`; it makes room for a new entry. ## Why a warm answer is not bitwise the cold one

Verdict: PARTIAL. The mechanism is visible in code; the numeric size of the difference is not measured here.

1. Cold prefill cuts the prompt into pieces of the engine chunk (`01905000` returns the `HALOGEN_PREFILL_CHUNK` value via `01905050.c:9`; 32768 per the banner), counted from token 0. In `018680b0.c` (~lines 55-110), when the piece is longer than the chunk size `iVar5`, snapshot positions are placed at `(offset % iVar5)` rounded down to a multiple of 64 (`& 0x7fffffc0`), relative to the current done position `param_2[4]`. So a snapshot (O(1) DeltaNet state after position p) can land on any multiple of 64 inside a chunk, not only at chunk ends.
2. Mode 1 ("bitwise resume") forces stores onto chunk boundaries: `01860720.c` (~lines 95-101): for `mode < 2` the store position is `iVar2 = n - n % chunk` (chunk at `param_2+0x68`); `018680b0.c:46-55` for `mode < 2` clips each piece at that boundary. A resume then restarts at a multiple of the chunk, so the remaining chunks are the ones the cold run used.
3. Mode 2 ("resume-anywhere") stores at the prompt end (`iVar2 = min(param_5, param_4)`) and at the tail checkpoints above. A resumed request starts its first chunk at that position `p`, so its chunk boundaries are `p, p+32768, ...` instead of `32768, 65536, ...`. Inferred: the chunked DeltaNet scan (dn_chunk_forward, `019d7b70`) and the prefill GEMM tiling group and reduce differently when the chunk start moves, so the recurrent state and the suffix K/V differ in low bits.
4. The snapshot is a raw copy: `018fe4f0.c` hands device pointers and byte counts to a copy callback with no conversion step. Inferred: saving adds no rounding, so the loss of bitwise equality comes from the changed chunk grouping (and the 64-token snapshot alignment), not from a lossy snapshot. Whether the engine rounds the state between chunks in a way that depends on chunk start was not read from the kernels.
5. Composable mode (SEG) is a further deviation by its own banner: about one quantization step, and the message-boundary split is a "resume seam".

What remains: kernel-level confirmation of which reductions depend on chunk start (dn_chunk_forward, prefill GEMM tile split) and a measured warm versus cold logit difference.

## HALOGEN_ADMIT_CHUNK

Verdict: CLOSED for what the setting does; PARTIAL for why it is bitwise.

- `0182ba00.c:1046-1049`: `HALOGEN_ADMIT_CHUNK` parsed with `strtol` into the admit-chunk value (`local_1324` low). `0182ba00.c:1074` prints the sentence only when the value is `>= 0`: "... prefills in pieces of %d tokens with a decode tick between them (HALOGEN_ADMIT_CHUNK; 0 = the engine's own chunk, which keeps the admitted prompt bitwise its alone self; -1 = the whole prompt at once)". The `%d` comes from `FUN_0182ea00(&local_1458,1)` (126 B; calls the chunk getter `01903630` and `01905000`).
- `HALOGEN_ADMIT_TICKS` (`0182ba00.c:1054-1060`, minimum 1) is the number of decode ticks between pieces.
- Why 0 is bitwise (inferred): the piece size equals the chunk the prompt would use alone (`HALOGEN_PREFILL_CHUNK`, 32768 here), so chunk starts are 0, 32768, ... as in a lone run; the decode ticks only interleave other streams. A smaller value moves the chunk boundaries and changes the grouping (same mechanism as the warm cache difference). `-1` is the whole prompt in one piece.

What remains: the scheduler code that applies the value (around `01846b20` and `0184be30` prefill_chunk_log) was not traced to the exact clamp.

## HALOGEN_CACHE_PRUNE_OLD

Verdict: CLOSED.

- `01854e90.c:347-355`: `getenv("HALOGEN_CACHE_PRUNE_OLD")`; the flag (`puVar9 + 0xc`) is true only when the value is exactly "1" (`*pcVar12 == '1'` and next char NUL). Any other value leaves it false.
- Boot scan of `HALOGEN_CACHE_DIR` (`01854e90.c:357-470`): `opendir`, for each non-dot entry that is not this configuration's own name (length and `bcmp` against the own name, `01854e90.c:363-367`), join path, `stat`, must be a directory. A directory that does not look like a fingerprint-named configuration directory is left alone. (That the call at `01854e90.c:~441` is the removal on the pruning path is inferred from the call order and the "removed another configuration's subtree" string; the rest of the loop past line 470 was not read.)
- Without the flag, other configurations are counted and kept: "prompt cache on DISK: %d other configuration(s) hold %.2f GiB there (a different engine, weights, context or lever); kept, not read (HALOGEN_CACHE_PRUNE_OLD=1 removes them at the next start)".
- With the flag the messages are "removed another configuration's subtree %s (%.2f GiB; HALOGEN_CACHE_PRUNE_OLD=1)" and "pruned %zu other configuration(s), %.2f GiB freed". Observed in analysis/evidence/engine-0.17.3-run.log lines 57-58: subtree `a665fe16b2767d6d` (60.25 GiB) removed, 1 configuration pruned, at the 0.17.3 start.
