# Sampling host side, second pass: U16, U23, U15

Method. Ghidra address = ELF vaddr + 0x100000 (objdump shows vaddr). Where Ghidra cut a decompile short, I read `objdump -d binaries/flash_serve` (output cited as `vaddr: instruction`). Kernel slices are in work/kernels-spec (`<kernel>.s:line`). VOP3 instructions that the slice printed as `.long` were decoded by hand from the two dwords; those are marked "hand-decoded". "Inferred" marks anything not read directly.

Key finding for U16 and U15: the earlier "no call site" result was a Ghidra artifact. The host launches the kernels inline: `leaq <descriptor>, %rdi` then `hipLaunchKernel`. The descriptor addresses are the PTR_FUN_019f63xx slots (not the stub functions), so `grep <stub addr>` finds nothing, and Ghidra ends the decompile of the launching function at `__hipPushCallConfiguration` ("does not return"). The launches are in the tail of accept_probs (01909e50), which Ghidra truncated at 1811 bytes; the real function runs on past 0x180a750.

Descriptor to kernel (from 01968680.c registration, lines quoted by the first agent plus these): 0x18f63c8 k_accept_prob_f32 (01968680.c:9-11), 0x18f63f0 smpg_max, 0x18f63f8 smpg_mass, 0x18f6400 smpg_pick (01968680.c:38-39), 0x18f6408 smpg_accept_final (01968680.c:43-44), 0x18f6410 qwrite, 0x18f6418 rmass, 0x18f6420 rpick (01968680.c:59-60). Inline launch sites (objdump): pick 1808df1, accept_final 180a59f, k_accept_prob_f32 180a72a, rmass 180ade2, rpick 180aff8.

## U16 which mode value of k_smpg_accept_final is greedy

Verdict: CLOSED. The argument is not a greedy-vs-sampled switch. It is the value of HALOGEN_S3_FALSIFY (default 0). Mode 3 forces acceptance of the fall-through row; any other value, including the default 0, rejects it.

Evidence, launch of accept_final inside accept_probs:
- `180a3d1: movl 0xf51c0(%rip), %r12d   # 0x18ff598` then `testl %r12d,%r12d; je 180a5ca`. 0x18ff598 is DAT_019ff598, set by FUN_0194bd50 = HALOGEN_SAMPLE_BLOCKS (default 0x40, clamp 0..0x100; 0194bd50.c: `getenv("HALOGEN_SAMPLE_BLOCKS")`, `return 0x40`). Blocks != 0 takes the SMPG path, blocks == 0 takes the plain k_accept_prob_f32 path at 180a5ca..180a72a.
- SMPG path argument block: `180a4b7: movl $0x3ca00, 0xc(%rsp)` (int 0, 248320, equals the id bound 0x3ca00 seen at 1734e1: `cmpl $0x3ca01, %ebx` in parse_request_json; so it is the vocab size, inferred), `180a4bf: movl %eax, 0x184(%rsp)` with eax from `180a481: movl 0xf5121(%rip), %eax   # 0x18ff5a8` (int 1 = mode), `180a4c6: movl %r12d, 0x180(%rsp)` (int 2 = SAMPLE_BLOCKS). The pointer array puts them at kernarg 0x30, 0x34, 0x38 (`1d0(%rsp)=&0xc(%rsp)`, `1d8=&0x184`, `1e0=&0x180`), and the kernel reads the second as mode (`s_load_b128 s[12:15], s[0:1], 0x30`, s13 = mode; `s_cmp_lg_u32 s13, 3` from the first agent, sampling-host.md U16).
- 0x18ff5a8 is filled by `180a99c: callq 0x184bd90` (Ghidra 0194bd90) under guard byte 0x18ff5b0 (`180a9a1: movl %eax, 0xf4c01(%rip)  # 0x18ff5a8`). 0194bd90.c: `getenv("HALOGEN_S3_FALSIFY")`, `__isoc23_strtol(pcVar1,0,10)`, else `return 0`.
- The plain path passes the same value as the second int of k_accept_prob_f32: `180a66a: movl $0x3ca00, 0x120(%rsp)`, `180a675: movl %eax, 0xc(%rsp)` (eax from 0x18ff5a8), pointer slots 0x1c8 and 0x1d0. Whether k_accept_prob_f32 uses it as 3-means-force-accept was not read (inferred: same role).

Greedy never reaches either launch: accept_probs, sample_rows and residual_sample exit with "temperature 0 is the GREEDY path and must stay on argmax()" for temp <= 0 (index.tsv strings for 019085c0, 01909e50, 0190aa50). Greedy is therefore not a mode value of this kernel; it is a different code path that does not call it.

Consequence for U20: HALOGEN_S3_FALSIFY is no longer "no consumer found". Its only consumer is this launch (and the k_accept_prob_f32 twin). It changes a kernel argument, not host data; 3 makes the fall-through row accept instead of reject (kernel side per the first agent: `v_cndmask_b32_e32 v2, 1.0, v3, vcc_lo`). That is a falsifier that deliberately accepts bad rows, consistent with the METHOD 37 wording of the other flags (inferred).

Remains: which rows reach the kernel's fall-through block in a normal run (so what mode 0 rejects). Runtime check: set HALOGEN_S3_FALSIFY=3 and compare acceptance counts (not run).

## U15 kernel-side meaning of SampleRow +4 (top_k) and +0xc (min_p), and +8 (top_p)

Verdict: CLOSED for the gating rules of +4 and +8; PARTIAL for exact thresholds. +0xc corrected: it is min_p, and the first agent's `v_cndmask ... s33` in pick was a mis-decode.

Correction to sampling-host.md U15. Slice lines such as `.long 0xd4130000` followed by `v_cndmask_b32_e32 v1, s33, v10, vcc_lo` are one 8-byte VOP3 compare, not a compare plus a select. Hand-decoded:
- k_smpg_pick: dword0 `0xd4130000` is op 0x013 (v_cmp_le_f32), vdst s0; dword1 `0x02021421` is src0 = 0x21 (s33 = row+0xc), src1 = 0x10A (v10). pick slice lines 550-551 (`.long 0xd4130000 ... // 0000002196DC`, next line `02021421`). v10 is `exp((l - lmax) * (1/T) * log2e)` (`v_mul_f32 v10, 0x3fb8aa3b, v10; v_exp_f32 v10`, pick slice lines 548-549). So the test is `min_p <= w` with w = exp((l-lmax)/T) in (0,1]. `s_and_b32 s9, vcc_lo, s0` (line 552) then combines it with `vcc` from `v_cmp_le_u32 vcc_lo, s30, v11` (line 546, key above the top-k/top-p threshold in scratch). A token is eligible only if both hold.
- k_smpg_mass: dword0 `0xd41c0001` is op 0x01c (v_cmp_nle_f32), vdst s1; dword1 `0x0202101F` is src0 = 0x1F (s31 = row+0xc), src1 = 0x108 (v8). mass slice lines 719-721: `v_exp_f32_e32 v8, v8; .long 0xd41c0001; (0202101F)`. s1 = (min_p > w). Next, `v_add_f32 v7, v4, v8` and `s_or_b32 vcc_lo, s0, s1; v_cndmask_b32 v4, v7, v4, vcc_lo` (lines 722-724): the weight w is added to the running mass only when neither the rank filter (s0) nor min_p (s1) excludes the token. So min_p also trims the normalising mass.
- k_smpg_accept_final: `v_cmp_nle_f32_e32 vcc_lo, s15, v0` (accept_final slice line 306, real encoding `7C38000F`), s15 = row+0xc, v0 = the exp numerator: reject when min_p > the token's relative weight, as the first agent noted.
- Row +4 and +8 loads: mass loads the whole 16 bytes at once, `s_load_b128 s[28:31], s[4:5], null` (mass slice line 16): s28 = 1/T, s29 = top_k, s30 = top_p, s31 = min_p (uses: `v_div_scale_f32 v2, null, s28, s28, 1.0` line 653; s29 line 164-166; s30 lines 176-178, 216-219; s31 line 721). pick and rpick load only +0x0 and +0xc (and +0x10 block), which is correct because top_k and top_p were already turned into a threshold in SmpScratch by mass and level; they read the threshold from scratch (`s30 = SmpScratch+0x4040` per the first agent).

top_k and top_p semantics (same gate in k_smpg_mass, k_smpg_level<N>, k_sample_f32, k_accept_prob_f32, k_resid_sample_f32):
- Gate text, mass slice lines 164-179: `s_cmp_gt_i32 s29, 0; s_cmp_lt_i32 s29, s38; s_and_b32 s19, s0, s1` then on failure `s_cmp_gt_f32 s30, 0; s_cmp_lt_f32 s30, 1.0`. Same sequence in level<0> (`s_cmp_gt_i32 s21,0`, `s_cmp_lt_i32 s21,s18`, `s_cmp_gt_f32 s22,0`, `s_cmp_lt_f32 s22,1.0`, lines 147-157), k_sample_f32 lines 358-370 (s37/s38), k_accept_prob_f32 lines 344-356 (s13/s14), k_resid_sample_f32 lines 342-354 (s37/s38).
- Reading it: top_k is active when 0 < top_k < N, where N is the kernel's first int argument (mass: `s_load_b64 s[38:39], s[0:1], 0x28`, s38; level: `s_load_b256 s[12:19]` s18 = kernarg 0x18). N is the vocab width; host passes 0x3ca00 = 248320 (see U16 evidence, inferred as vocab). Else top_p is active when 0 < top_p < 1.0. If both are active, top_k wins and top_p is ignored (the second test sits in the failure branch of the first). top_k = 0 or >= N and top_p outside (0,1) means no rank filter. The wire parser's "0 = off" for top_p matches (wire-protocol.md:69).
- top_k branch (inferred from structure): level<0..3> are four passes of an 8-bit radix select over the 32-bit sortable key (`v_not_b32`/`0x80000000` key transform in pick lines 550-ish, partial counts in scratch +0x400), finding the key of rank top_k; the result lands in scratch and is the threshold pick compares against. top_p branch: mass sums partial masses into a total (loop over `s39` partials, mass lines 183-205), then converts `top_p * total` to a 64-bit target through f64 ops (`v_cvt_f64_f32 v[1:2], s30` line 228 and `v_trunc/v_floor/v_fma_f64` with 0xc1f00000 = -2^32, lines 232-244); the later levels select the key where cumulative mass reaches that target (inferred; several compare opcodes are `.long`-encoded and were not hand-decoded). Nucleus is therefore on the temperature-scaled softmax, applied before min_p in the accept and pick tests (order of the tests, not of an explicit pipeline, inferred).
- Order matches the wire doc open item (wire-protocol.md:259 "Sampler order (top_k, top_p, min_p, temperature)"): temperature scales the logits first (1/T in s28 is applied to every exp), then rank filter (top_k xor top_p), then the min_p weight test, then the draw.

Remains: exact tie handling at the radix threshold (keep ties or drop), and whether cumulative top_p mass includes the threshold token (`>=` vs `>`); both need the level<3> final compare decoded or a runtime probe with a crafted row.
