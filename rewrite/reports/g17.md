## What each kernel does (all confirmed by MATCH)

- ht_items: `slots` writes records {ids[j], i - 20j (or 5j), j, j+1}, tok[i] = i/10, rank[i] = i. `group<G>` is one 128-thread block: stable-sort rank, count per expert, `ceil(count/G)` items per expert, A 5 records and B 20 records per item, total items. Matches htitem-r3.md.
- ht_rot: all five are one wave32 per 128 values, 4 values per lane. 4-value Sylvester butterfly in registers, then lane xor 1,2,4,8 (DPP) and 16 (permlanex16), where the lane with the bit set negates itself before adding the partner. `rot_in`, `rot_rows`, `rot_rows_h` fold the f16 column scale into the first stage with `fma_mix` (p = h0*x0 + h1*x1, m = h0*x0 - h1*x1). f16 outputs use `fma(r, 1/sqrt(128), +0)` (turns -0 into +0); bf16 outputs use v_mul then RNE; `rot_out` and `rot_out_f32` multiply the scale after the transform. `rot_in` has the 2560 row width built in (20 blocks).
- ht_deq_t: unified decode rule of ht-decode.md (window at bit `B*(255-j)` of the reversed circular tile bit string, hash 0x83dcd12d, byte sum + 0x6400 as f16 bits, `fma_f16(.., 0x1eee, 0xc931)`, bf16 RNE), tile id `(q*K16+ct)*8+rt`, 3 bit uses 24 words per tile. Checked bitwise for 3 and 4 bit.
- ht_deq_orig: one block per 128x128 region; dequantize (f16 value kept as f32), 128-point WHT over columns (32-point in bits 0..4, then 4-point in bits 5,6, bit order natural), * 1/sqrt(128), * a[col] (fma_mix -0); same over rows with b[row], bf16 RNE, out[(128*rb+row)*K + 128*cb+col]. `flag == 0`: cb = blockIdx.y, rb = blockIdx.x, else swapped. The `bool` and `16|8` template arguments (block 512 or 256) give bitwise identical results to the same rewrite.
- ht_tg_sum is k_ht_rot_out_f32 preceded by a split-K sum (partial stride a*b floats).
- ht_tg / ht_tg3: grid (token tiles of 64/128, N/128 or N/256, splits). Weights are the WMMA A operand, activations the B operand, 16 K per WMMA, accumulation from zero in K order over the split's range of 128-blocks. With a partial pointer the raw f32 accumulators are stored (`part[z*M*N + tok*N + col]`); with a null pointer the 128-point rot-style transform (4 in registers, 5 lane stages) * 1/sqrt(128) * sv, bf16 RNE. tg3 covers 256 rows per block (two 128-row blocks), tg 128.
- ht_moe:
  - `dn<B,8,G>`: tile 128 rows, K 640 (40 steps), wave w handles tokens begin+16w..; rows are the WMMA B operand; transform tree is high bits first (subtile index bits j0,j1,j2 in registers, then lane xor 1,2,4,8); G and the 8 do not change the code (listings identical).
  - `gu<B,8,G>`: tile 256 rows (gate rows = subtiles 0..7, up rows = 8..15), K 2560, activation rows via `ids[pos]`. Epilogue: transform gate and up, * 1/sqrt(128), * sv (gate at tile*128+16c, up at +640), silu `x / (1 + exp2(x * -log2e))` with IEEE division, product with up, * suh, a second 128-point transform (the next layer's input rotation) with the f16 output `fma(r, 1/sqrt(128), +0)`.
  - `gu3`, `gu2`, `gu2w` (token-major tiles, weights as A operand): same inputs and per-element math but the epilogue goes through LDS and a wave owns one token with the rot-style tree (4 in registers, 5 lane stages), which is a different association from gu. gu3: 16 waves, 128 tokens; gu2: 8 waves, 64 tokens. `gu2w<..,6,0>` is bitwise identical to gu2 on all specs.
  - `dn3`: two consecutive 128-row tiles per block (16 waves), 128 tokens. `dn2`: one tile, 64 tokens. `dn2x`: two tiles, 64 tokens. `dn2w` equals dn2. All use the rot-style tree, then * 1/sqrt(128) * sv[expert*2560 + col], bf16.
  - The `E` template argument (0,1,2) and the other trailing integers do not change results on any spec; the listings differ only in instruction scheduling and a dequant window variant that decodes the same values.
- Block sizes: dn/gu 256, gu3/dn3 512, gu2/dn2/dn2x/tg 256, tg3 512, deq_orig 512 or 256, rot 256.

## Notes
- All rewrites have `#pragma clang fp contract(off)` and use `__builtin_fmaf` explicitly where the listing has a fused op (second addendum).
- The silu path calls `x / (1.0f + e)` without fast-math, which compiles to the same div_scale/rcp/div_fmas/div_fixup sequence as the vendor.
- WMMA: `__builtin_amdgcn_wmma_f32_16x16x16_f16_w32`; the vendor's two operand orientations (tokens as A in gu/dn, as B in gu3/gu2/dn3/dn2/tg) both match the same builtin, so the hardware dot product order does not depend on the operand role.
- Reading method: listing slices in `work/kernels-dequant/` omit nothing, but the objdump leaves VOP3 words it cannot decode as `.long`; those were decoded by hand from opcode fields (0xd72c mul_lo, 0xd73d lshrrev_b64, 0xd73c lshlrev_b64, 0xd7006a add_co, 0xd4c4 cmpx). `v_cndmask_b32 ..., vcc` lines that follow a `.long` are the second dword of that VOP3 instruction, not a select.
