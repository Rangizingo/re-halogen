## Cause (same mechanism in all five)

AMD VALU ops return the first NaN operand in source order (src0, src1, src2), with its sign. A NaN made by an invalid op (0*inf, inf-inf) is the default NaN 0xffc00000. hipcc rewrites the math in ways that are exact for numbers but pick a different NaN: (a) it commutes multiplies, (b) it folds `fma(x, y, -0.0)` to a plain `v_mul` with swapped operands, (c) it moves a negation from a product to its input. All five mismatches are NaN-vs-NaN, sign only.

### vis_rope (`k_vis_rope`)
Candidates, ranked: 1. negation placed on the multiplicand instead of the product; 2. operand order of the fma (c, x1 vs x1, c); 3. sin/cos of a special angle. Only 1 fits: failing element 5049 is `k[e]` (row 1, head 6, e=9) with `y2` = 0xff800000 and pos = 0, so sin = 0 and `s*y2` is 0*inf = 0xffc00000.
- Vendor: `:59738 v_mul_f32 v13, v12, v8` (s*y2), `:59743 v_fma_f32 v13, v11, v9, -v13` negates the product after the multiply: 0xffc00000 becomes 0x7fc00000. Same at `:59736`/`:59745` for q.
- Rewrite: `rw:152 v_mul_f32_e64 v8, v11, -v8` then fmac: negates y2 first, the multiply returns 0xffc00000.
- Fix: `vis_rope_c.hip`, inline asm `v_fma_f32 d, c, x1, -p` for `q[e]` and `k[e]`. Failing elements in the refuter run: 7 of 221184, all this pattern.

### ht_deq (`k_ht_deq_orig<*>`)
Candidates, ranked: 1. `fma(b, y, -0.0)` folded to a multiply with y first; 2. WHT add/sub operand swap (`lo + hi`); 3. bf16 rounding of NaN. Only 1 fits: the 2 failing elements (94385, 97457) are rows 245 and 253 of column 305; `b[245]` = `b[253]` = 0x7e00 (+NaN) and `a[305]` = +inf, so the row transform of column 305 yields the default NaN (-NaN) in `y`. `f2bf` keeps the sign bit, so the f32 sign shows in bf16.
- Vendor: `:423695 v_fma_mix_f32 v1, v1, v18, neg(0) op_sel_hi:[1,0,0]`: b in src0, y in src1, so b's +NaN wins (0x7fc0). Same for a at `:423313`.
- Rewrite: `rw:2243 v_mul_f32 v14, v17, v14` (v17 = y, v14 = cvt(b)) and `rw:2252 v_mul_f32 v11, v11, v13`: y first, so y's -NaN wins (0xffc0).
- Fix: `ht_deq_c.hip`, `fma_mix_nz()` asm `v_fma_mix_f32 d, half, y, neg(0) op_sel_hi:[1,0,0]` at both sites. Adds/subs of the WHT needed no change (dense specs below MATCH).

### i4r_gu (`k_i4r_gu_epi`)
Candidates, ranked: 1. same fma(-0.0) fold with swapped operands, on the b products t1, t3 (the pair swap fits: `s = fma(p, b, t)` and `d = fma(p, b, -t)` take opposite signs of t, so a flipped t NaN swaps the pair); 2. operand order of the butterfly `cndmask(-x, x) + partner`; 3. the `silu` divide sequence. Candidate 2 checks out equal (vendor `:21133 v_add_f32 v8, v8, v27` with the cndmask result in src0; rewrite `rw:122 v_add_f32 v5, v5, v36`, same order). Candidate 1 fits and fixes it.
- Vendor: `:21343 v_fma_mix_f32 v0, v13, v0, neg(0) op_sel:[1,0,0] op_sel_hi:[1,0,0]` and `:21346 v_fma_mix_f32 v5, v14, v5, neg(0) ...` (b in src0); gs `:21244`, us `:21264` likewise (a in src0).
- Rewrite: `rw:366 v_dual_mul_f32 v6, v7, v6 :: v_dual_mul_f32 v5, v5, v32`, `rw:367 v_mul_f32 v7, v10, v31` (prod first, b second); `rw:258 v_mul_f32 v11, v11, v17` (e*C first, a second).
- Fix: `i4r_gu_c.hip`, `fma_mix_nz()` at gs, us, t1, t3.

### dnc_ut (`k_dnc_ut`), out1 only (out2 already matched)
Candidates, ranked: 1. commuted `tij * vm` (and `tij * kk`); 2. fma accumulate order; 3. the exp / Gram fma chain. First failing element 15991 = t 2, head 28, d 119, out1. Candidate 1 fits: a T entry is -NaN (0xffc00000 from 0*inf in the Gram dot) and `vm` is bf16 +NaN; vendor 0xffc00000, rewrite 0x7fc00000.
- Vendor (rotated unroll by 2): `:2107 v_mul_f32 v27, v27, v29` (tij * vm), `:2103 v_mul_f32 v31, v27, v31` (tij * kk), `:2108 v_mul_f32 v29, v11, v31` (beta * ...), `:2113 v_fmac_f32 v25, v12, v29`, `:2117 v_fmac_f32 v24, v27, v11` (o1 += (tij*vm) * beta).
- Rewrite: `rw:411 v_mul_f32 v30, v30, v31` (kk * tij), `rw:412 v_mul_f32 v29, v29, v31` (vm * tij): tij is src1.
- Fix: `dnc_ut_c.hip`, asm `mulv` / `fmav` (v_mul_f32 / v_fma_f32) in the output pass with the vendor operand order.

### dnc_ut3 (`k_dnc_ut3`)
Same candidates as dnc_ut. Same cause, but the vendor ut3 accumulate order differs from ut: `:3848 v_fma_f32 v0, v18, v33, v0` is beta[m] * (tij*vm) + o1 (beta first), where ut has the product first. First attempt (copying the ut order) MATCHed the refuter spec but failed on my NaN spec; fixed to the ut3 order. Other ut3 lines: `:3815 v_mul_f32 v0, v4, v6` (vm*beta), `:3817 v_dual_mul_f32 v4, v6, v5` (beta*kk), `:3841 v_mul_f32 v33, v31, v33` (tij*vm), `:3843 v_mul_f32 v38, v31, v38` (tij*kk), `:3851 v_mul_f32 v33, v18, v34`, `:3860 v_fma_f32 v4, v19, v33, v4`.
- Fix: `dnc_ut3_c.hip`.

## Limits

- The asm pins the operand order only where the listing was read and a NaN spec failed or the site is in the same expression; other float ops still go through hipcc. The two data sets per family (0.4% and dense) are the evidence for those, not a proof for every NaN path.
- Seeds 31..33 share one data file per float buffer (only seed-driven buffers such as ht_deq `w` change).
- `fma_mix_nz` reads the half from the low 16 bits; the vendor sometimes uses `op_sel:[1,0,0]` (high half). Same math.
- `i4r_gu_c.hip` comment lines for the vendor cites were corrected after the runs (comment only, no code change).
- Not run: ht_gemv*, other families. `kernels-disasm-v2/` and `~/g24/isa/` are not in git.
