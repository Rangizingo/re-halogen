## How the listing was read

llvm-objdump prints some VOP3 words as `.long 0xd4.... / 0xd7....` followed by a bogus `v_cndmask_b32_e32` line. The second dword of the pair is really the operand word of the VOP3 instruction (src0 bits 8:0, src1 bits 17:9, src2 bits 26:18, with src2 = 128 meaning inline 0). Decoded opcodes used here: `0xd73c` v_lshlrev_b64, `0xd700` v_add_co_u32, `0xd44a` v_cmp_eq_u32, `0xd44c` v_cmp_gt_u32, `0xd449` v_cmp_lt_u32, `0xd44d` v_cmp_ne_u32, `0xd441` v_cmp_lt_i32, `0xd454` v_cmp_gt_i64, `0xd414` v_cmp_gt_f32, `0xd41b` v_cmp_ngt_f32, `0xd41d` v_cmp_neq_f32, `0xd4c9`/`0xd4ca`/`0xd4cd` v_cmpx lt/eq/ne_u32, `0xd72c` v_mul_lo_u32 (v_mad_u64_u32 form), `0xd7390002` v_lshrrev_b16, and the VOP1 words `0x7e04....`/`0x7f04....` are true16 `v_mov_b16` (op 0x1c; llvm rejects them). Each decode was then confirmed by a MATCH against the vendor object.

## What each kernel does (evidence is in the .hip headers; line numbers are `kernels-disasm/codeobj_53000.s`)

hist: `out[i] = in[4i+1]`, `out[0x2800+i] = in[4i+2]`, `out[0x5000+i] = in[4i+3]` for i < 10240 (:30213-30248). Pure 16-bit copy, so the iota specs make it exhaustive.

count: grid-stride loop, `a[i] != b[i]` adds 1 to `out[0]` and takes `atomicMin` of the index into `out[1]` (:57587-57656). The vendor does one wave-level atomic add (bcnt) and one atomic min per wave; per-lane atomics give the same final integers. Specs start `out` at 0xffffffff so `out[0]` wraps; both sides wrap the same way.

route_hist: 1024 expert ids per block (4 per thread, 256 threads). Ids outside [0,512) unsigned, or at or past n, count as -1. `blk_hist[block*512 + e]` = block histogram; `rank[idx]` = number of earlier ids in the block with the same value (-1 counts as a value). See header cites :47510-47921.

route_scan: single block of 512 threads. Sums the per-block histograms per expert, inclusive Hillis-Steele scan over (total, nonzero) in LDS, writes the active-expert list, offsets, totals, and rewrites the histogram array in place as per-(block, expert) start offsets (:47949-48413).

route_scatter: `perm[rank[idx] + boff[block*512+e]] = idx`, `slot[idx] = that position`, for e in [0,512) (:48434-48486).

route_topk:
- `k_route_topk`: one block of 512 per row, LDS compare-exchange tree, ten rounds. Tie rule: the tree replaces a value only when the other one is strictly greater (v_cmp_gt_f32, :37085 etc.), so ties resolve by tree position and are NOT plain lowest-index. The same tree is kept. Softmax over the ten picks: `exp2((v - v0) * 1.442695)` (v_exp_f32), sum in order e0..e9, IEEE divide.
- `k_route_topk_w`: one wave32 per row. Order: larger value first; equal values: smaller `bitrev9(idx)` first (`v_bfrev_b32` then `>> 23`, :37512-37523 and the compare chains :37653-38117). The order is total, so any reduction order gives the same picks; five xor-butterfly steps keep the vendor shape. Same softmax tail.
- `k_route_topk_w_grp<G>`: k_route_topk_w plus a grouping stage in the same block: stable sort position of the 10*nrows expert ids, `rank`, `tok = t/10`, optional `inv` (null allowed), per-expert item count `ceil(cnt/G)`, 16-byte `HtItem {expert, tile, begin, end}` records (5 per item in A, 20 per item in B), total item count. Constraint: one block, nrows <= 8 (a second block would race on A/B; the vendor has the same property). Layout agrees with `analysis/closure/htitem-r3.md`.

route_logits (all use `v_fmac_f32` accumulation over a blockDim-strided k loop and a halving LDS tree, so the f32 summation order is fixed; bf16 x is widened by `<< 16`):
- w32 / x32: one dot per (token bx, expert by); `out[by*gridDim.x + bx]`.
- x32_m<M>: M tokens per block, expert = blockIdx.y; `out[ld*by + M*bx + j]`.
- rows<R,E>: R tokens and E experts per block (expert rows are `w + e*K`); `out[e*ld + R*bx + j]`.
- sg1<R,b> / rows_sg<R,E,b>: the plain block for blockIdx.x < arg32/R, plus the block with blockIdx.x == arg32/R which computes shared-expert gates: a 16-entry palette becomes a 256-entry LDS table of bf16 pairs, 32-element groups of 16 code bytes with an f16 scale, `v_dot2_f32_bf16` chains, `acc += scale*d`, wave xor-butterfly, sum over 8 waves starting from `0 + w0`, `1 / (1 + exp2(-1.442695 * s))`. rows_sg repeats it for E activation vectors (stride K elements) and writes E sigmoids. SgArg layout is in the .hip header; its fourth field (offset 0x40) is never read by the gate block.

## Open items and inferences

- Template argument `b` of sg1 and rows_sg: the two variants differ in code layout (b = 1 has a path guarded by `G <= 2048`, `s_cmpk_lt_i32 s4, 0x801`, that loads the scales up front). Every compare, including G = 2050 (N = 65600), matches the single rewrite, so the arithmetic order is the same. What `b` stands for beyond that is inferred as a scale-prefetch switch; not confirmed.
- SgArg field at kernarg offset 0x40 is unread in the gate block; the specs pass 0.
- NaN and inf inputs to the top-k kernels were not tested (the value ordering for NaN follows the vendor compare operands but no spec exercises it).
- route_scatter_pipe_* specs read file fills under `/tmp/g06/` on Ai-core, produced by the VENDOR route_hist and route_scan so that offsets and ranks are consistent. Rebuild with the two compare.py runs below.
