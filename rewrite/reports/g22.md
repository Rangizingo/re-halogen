Compiler notes (hipcc, gfx1151):
- `__fmul_rn` / `__fadd_rn` are contracted into `v_fma_f32` (seen in the rewrite's disassembly). All g22 files carry `#pragma clang fp contract(off)` and use `__builtin_fmaf` wherever the vendor fuses. The first runs of `k_i4r_fold` showed this bug: 1 bf16 ulp in about 1 of 7700 outputs, found only with full-range f32 inputs (bf16-valued inputs in `k_i4r_fold_rows` hid it). Those MISMATCH rows are not in the final table (it was regenerated from scratch after the last code change); they are in the archived pre-fix tables on Ai-core under `~/g22work/old/`.
- Fused f16 dot: the i4r_rows rewrites use `__builtin_amdgcn_fdot2` (v_dot2_f32_f16), the same instruction as the vendor, so accumulation is identical by construction.

Data note for the quantized expert and i4r specs: weights, LUT and scales share one blob buffer, so the spec fills it with f16 values in [0.01, 0.5] ("f16") or [-0.5, 0.5] ("f16s"). Random bytes ("u8") put NaN/Inf into scales and LUT in most rows; with NaN inputs the vendor and rewrite produced different outputs in about half the elements (first expert_h_warp u8 and f32 runs; archived table only). Cause not isolated; inferred to be NaN payload selection (operand order), not arithmetic. Those specs were removed, so NaN/Inf scale behaviour of the warp expert kernels is untested.

## Findings worth keeping

- `k_deq_aff<BITS,PAIR>`: AffDev (48 B at kernarg 16) = six u64: nibble base, 5th-bit plane base, scale base, scale row stride, d/dmin base, d/dmin row stride (byte offsets from `src`). PAIR=false: u32 {f16 scale, f16 offset} per 32 elements, value = fma(nib, scale, offset). PAIR=true (Q4_K-like): u16 {scale byte, min byte} per 32 plus u32 {f16 d, f16 dmin} per 256; value = fma(nib, d*sc, -(dmin*m)) with both products `v_fma_mix_f32 ..., neg(0)`, i.e. fma with a `-0.0` addend. `-0.0f` -> `0.0f` mismatches on `deq_aff_4t_edge` (d<0, sc=0, m>0, dmin=0).
- Expert layouts: gate/up weights W[e] = 1280 rows x 2560 (gate rows 0..639, up 640..1279), 640 outputs per slot; down W[e] = 2560 rows x 640. Quantized forms: LUT form = first 16 floats of the blob are the codebook, nibbles low first, one f16 scale per 32; AFF form = AffDev as above (down uses PAIR=false with the 5-bit plane). Warp kernels: a lane visits i = lane + 32t ascending, then a five-step shuffle (partners lane|16, +8 if lane<24, +4 if <28, +2 if <30, +1 if !=31); the grouped h kernel stages two rows of bf16 weights in LDS and gives the same sums.
- `k_i4r_rows<K>`: int4 weights (n-8) times one f16 scale per 128 along K; 64 rows per block, 4 lanes per row, each lane 32 weights per 128-block via `v_dot2acc_f32_f16` on f16 pairs (n-8, exact), scales applied per 128-block with `fma(scale_m, acc_m)` ascending, then xor-1 and xor-2 adds. rot/epi/fl/fl_o are the same GEMV with a fused activation producer (rot: x*su then 128-point Walsh-Hadamard; epi: the k_i4r_gu_epi pipeline) or a fused 10-slot fold (fl: ticket counter `ctr[tok*20 + blk/2]`, the 20th arrival folds and resets the counter; fl_o: slot taken from `sel[blockIdx/40]`).
- Walsh-Hadamard in gu_epi/fold/rot/epi/fl: 4-point in-lane transform (p0=a+b, p1=a-b, p2=c+d, p3=c-d; e0=p0+p2, e1=p1+p3, e2=p0-p2, e3=p1-p3), then xor butterflies 1,2,4,8,16, then `* 0x3db504f3`.

## Open items

1. HtItem group (k_i4r_rows_fl_g<4|2>, k_i4r_rows_gl_g x4): BLOCKED on a harness feature. The kernels read a table of 16-byte HtItem {expert, tile, begin, end} records plus two int arrays (analysis/closure/htitem-r3.md). The buffer fill kinds (zero, const, iota, rand, file) cannot make a table whose four fields differ; `file` needs a path on Ai-core that is not in the repo. Need: a fill kind with literal bytes (for example `{"kind":"bytes","hex":"..."}`) or an `i32` pattern fill. Decode state (inferred from the first 90 lines of k_i4r_rows_fl_g<2>, listing 1982330-1983490): item = blockIdx/80 (magic 0x66666667 >> 4), guard item < items-count (kernarg int array), HtItem at item*5*16 B, min(end-begin, 2) slot ids staged in LDS (`ds_store offset:2560`), x rows copied into LDS per slot (0x500 B stride), then the K=640 GEMV core as in k_i4r_rows. Not decoded further.
2. k_i4r_rows_gl<1|2>, gl_o<1|2> (about 4200 lines each): fused prelude/epilogue around the same GEMV core. The prelude (blocks with `blockIdx.x < nrot`) rotates activation rows (`v_fma_mixhi_f16 ... s49(0x3db504f3), 0` and `ds_store_b64`), the rest are GEMV blocks taking I4rSd (88 B at kernarg 72) fields; not decoded.
3. k_dv_quant (4-bit NF4 draft-vocab quantizer, listing 8793-14861, kernarg: x bf16*, dst int*, src int*, n, u8* q, scale-plane offset long, A=2560). Decoded so far: per thread one 32-value block (r = tid / (A/32), b = tid % (A/32), same as k_dv_quant8); absmax via v_max3_f32; each thread's 64 B LDS region (65536 B group segment / 1024 threads) is first filled with the 16 NF4 floats (-1, -0.6962, ..., 1); an 8-iteration loop tries scale candidates `sc_i = absmax * (float(i) * s9 + 1.0)` (`s_fmaak_f32 s0, s0, s9, 0x3f800000`; `s9` not yet traced), skips candidates with `!(2^-25 < sc)`, rounds to f16 and back (`v_cvt_f16_f32`, `v_cvt_f32_f16`), divides each x by it (IEEE), picks the nearest codebook entry as a count of 15 strict midpoint comparisons (`midpoint < t`; thresholds as f32 literals 0xbf590000, 0xbf1c0000, 0xbeeb0000, 0xbeae0000, 0xbe708000, 0xbe0d0000, 0xbd3a0000, 0x3d230000, 0x3df68000, 0x3e508000, 0x3e958000, 0x3ec78000, 0x3f008000, 0x3f248000, 0x3f5c8000), loads lut[idx] from the thread's LDS copy and accumulates squared error with `v_fma_mix_f32 -lut, scale_f16, x` then `v_fmac_f32 e, r, r`. Still to decode: the exact error accumulation order, the candidate selection rule (strict less or not, initial best), and the final nibble packing and stores (32 nibbles to 16 bytes at q + dst*1280 + 16*b, f16 scale at q + soff + dst*160 + 2*b per analysis/closure/dv-quant-r4.md). No harness blocker.
