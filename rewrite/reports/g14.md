## Blockers (exact)

- dn_t fold (`...Lb1E`): after the partial write each block does `global_atomic_add_u32` on a counter and the last of 10 slots per token (counter == 9) folds
  10 partials with f32 weights, a residual and a per-token scalar into a final bf16 buffer. The register `s[6:7]` used as the counter base is the x pointer advanced by `pos*0x500`
  (dn_t_4_8_0_1 listing, `@A63194`-`@A631DC`), and `s[4:5]` (the W pointer) is used as the final-output base after the compute loop reused `s4/s5` as scalars (`@A619E4`, `@A63594`).
  A probe with all five `HtFold` quad-words pointing at separate zeroed buffers (grid 200) changed none of them, nor x, ids, sv, w; only the partial `out` rows were written. So the pointer fields of
  `HtFold` are not decoded and the fold path never ran. Needed: the host-side `HtFold` layout (40 B, `analysis/closure/` has none) or a capture of a real launch.
- dn_ts, dn_g, gu_t sd path: take an 88 byte `HtSd` struct plus an int (kernarg 0x30 / 0x88): blocks below the int run the token path, the rest a dense path with integer division based tile
  mapping (`s_abs_i32 / v_rcp_iflag` sequences at `@95C460`, `@922158`). The struct fields (pointers, strides, extents) are not documented; not decoded.

## Facts proven by MATCH

- HT weight decode, 3 and 4 bit, is the unified rule of `analysis/closure/ht-decode.md` (window of 16 bits of the tile words read in reverse as one LE bit string, start
  `BITS*(255 - (8t + c)) mod 256*BITS`), hash `x*0x83dcd12d`, byte sum plus 0x6400 as f16 bits, weight `fma_f16(1024+S, 0x1eee, 0xc931)`; column `8h + c`, dot pairs (c0,c1)..(c6,c7)
  with `v_dot2acc_f32_f16`. This confirms the closure doc's 3-bit claim end to end on random bytes.
- Wave partials: own + other half, wave 0 sums waves 0..7 from `0 + P0`, 128-point WHT (j stages 1,2,4 then lane xor 1,2,4,8; lane with the bit set computes `partner - x`), then
  `* 0x3db504f3` (vendor literal; the nearest f32 to 0.0883883506 is `0x3db504f4` and flips 1-ulp f16 outputs), then `* sv`.
- dn: down matrix 2560 x 640, tile = 128 rows, wave w owns column tiles 5w..5w+4; output bf16 RNE of `sv * (wht * c)`. gu: gate_up 1280 x 2560, tile = 256 rows (128 gate rows then 128 up rows),
  wave w owns 20 column tiles, `Z = U * (G / (1 + exp2(G * -1.4427)))`, second WHT with a fused first stage (`fma(Z[2m], su[2m], rn(Z[2m+1]*su[2m+1]))` and the minus form), output
  `v_fma_mixlo_f16(o, c, 0)` (f16 of the exact product).
- Item addressing: dn/gu take `HtItem{expert, tile, begin, end}` records (x row `min(begin,end-1)`; gu goes through `tok[]`; write only if end > begin). dn_t: `wg = 20*pos + tile`, expert `ids[pos]`.
  gu_t: `wg = 5*pos + tile`, x row `pos/10`. gu_ts<B,S>: block of 8/S waves, `wg = (pos*5+tile)*S + split`, per-wave partials to scratch (slot 1024 B at `((pt*8)+gw)*1024`), atomic counter per `pt`,
  last block finishes. gu_gs<B,8,G>: one wave per block, `wg = 8*I + split`, `I < 5*(*cnt)`, G tokens share the decoded weights, partial slots indexed by `(begin+g)*5 + tile`.
- A harness note: a kernel with a K-split + atomic counter only matches if the scratch is big enough for the vendor's slot indexing (8 MiB Pf, 4 KiB Pj in the ts/gs specs); an undersized Pf gives
  `hipErrorIllegalAddress` in the vendor run.

## Specs and sensitivity

- dn specs: 160 items (dn) or 800 grid blocks (dn_t, 40 positions); gu: 80 items / 400 blocks / 400-1600 blocks (ts, by S) / 320 blocks (gs, 40 records). Item and record arrays come from
  `struct.pack("<4i", ...)` files in `/tmp/g14` on Ai-core (`file` fill); recipes: dn items `((p+t)%3, t, p, p+1+(t%2))` p<8 t<20; gu items `((p+b)%2, b, p, p+1+(b%2))` p<16 b<5;
  gs records for item m<8: expert m%2, begin 4m, end begin+1+(m%4), tiles 0-4, cnt = 8.
- `_small`: x in +-0.001 (gu outputs reach f16 subnormals). `_edge` (gu family): x in +-3, sv in +-40 (exp2 overflow, SiLU saturation).
- dn writes bf16: a 1-ulp f32 error shows in about 1 of 65k outputs, so dn data alone is weak evidence for constants; they are verified from the listing.
