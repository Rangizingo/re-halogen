## Finding 1: the repo listings hide instructions

`kernels-disasm/codeobj_*.s` printed VOP3 and VOPC instructions as `.long 0x...` followed by a bogus `v_cndmask_b32` (the next dword is the 2nd word of the undecoded instruction): 13,181 such lines in codeobj_1513000. `v_add_co_u32 v65, vcc_lo, 0x200, v6` at 0x197bf0 was shown as `.long 0xd7006a41`, so v65..v67 looked "never written". Re-disassembled with Homebrew LLVM 23 (`/opt/homebrew/opt/llvm/bin/llvm-objdump -d --mcpu=gfx1151 work/fatbin/codeobj_1513000.hsaco`): 0 `.long` lines. The coordinator regenerated all four objects in `kernels-disasm-v2/`. Cites below are code object addresses (identical in both listings).

## bt2<2,0>, <32,0>, <64,0>

Common: same tile loop as bt2<0,0> (listing 0x1b2900); only one operand source changes. All three are style A (the `-1e29` test is present in each listing).

- bt2<2,0> (0x197800). Probe 2: V fragments are loaded once before the loop from pool pages 0..3, not through the page list. `v_add_co_u32 v65..v67 = 0x200/0x400/0x600 + (256g+col)` (0x197bf0-0x197c28), pointer = Vp + 8*(((256g+col)|128w|16c)|X), X in {0,0x200,0x400,0x600}; 32 `global_load_b64` at 0x19801c-0x198114 feed 8 wmma at 0x1984a0. Rewrite: `vpg = k>>2` instead of the page list (page j = k>>2, row r = k&3). Same idea as g18b's bt2<1,0> but on V. MATCH first run.
- bt2<32,0> (0x1a9400). Probe 32: no K loads. The S B operand is built from the tile counter s0 (`v_pk_add_u16` at 0x1a9ea0-0x1a9eb4, `v_and 0x70007`, `v_or 0x3f803f80`, `v_mov_b16` shuffle after it): chunk c, element k is bf16 `0x3f80 | ((t + c + (k&7)) & 7)`, same in every lane, not wave dependent. Rewrite matches bitwise.
- bt2<64,0> (0x1adf00). Probe 64: no V loads. `s_mov_b32 s5/s7/s9/s11 = 0x3f803f80` (0x1ae434) and s4..s29 = `0x3f803f80 | ((u+q)&7)` (u = tile counter s18) copied into v77..v180 for the 8 wmma at 0x1ae83c: chunk c, element k is `0x3f80 | ((t+c+(k>>2))&7)` when k%4==0, else `0x3f80`. Rewrite matches bitwise. g18b's "kernarg pointers" reading was the same decode artifact.
Fill choice: g18b's bt2 spec (rand q,k in [-2,2], v in [-1,1], gate [-4,4]): non-degenerate and ordinary.

## qs<2,0> and qs<3,0>

Listing facts (kernel at 0x173300): V is read as two `ds_load_b128` per lane at `w*0x3000 + 0x800 + 48*col + 768*c + {0,16}` (`v251 = v1|v2|0x800`), 12288 bytes per wave, 2048 to 51200 in total. Every `ds_store` in the kernel (51200 key index table, 64336, S tile from 59472, P tile 0..2047, O merge) lies outside that range. The kernel has no `ds_store_b16` for V (the `ds_store_b16` lines g18b saw belong to the next kernel, qs<4,0>). There is no global V load either: the only kernarg `s_load` of Q/K is `s_load_b128 s[12:15], s[0:1], null` at 0x1736a4 (V at kernarg 0x10 is never loaded). So the PV product reads 48 KiB of whatever earlier workgroups left in LDS.

Proof that the vendor result is undefined: spec attn_qs_0_0 (N=203, seed 1), 5 back-to-back runs of vendor qs<2,0> in separate processes: 25,987 / 26,602 / 26,042 / 21,078 of 37,120 output bytes differ from run 1; only 2,355 of 18,560 bf16 outputs are identical across all 5 runs, and the outputs are garbage (values near 2.5e35, many NaN). This is every output, not a subset, so `exclude` would remove the whole output and test nothing. I did not use it.

Conditional verification with a priming kernel (scratch driver, not in the repo): a copy of `run_kernel.cpp` (`~/g18c/rk_prime.cpp` on Ai-core) launches `prime.co` first (1000 blocks x 256 threads, 64340 bytes dynamic LDS, halfword i := 0x3f80 + 8*(i&15)), then the real kernel. With that pattern the vendor is deterministic and the rewrite matches bitwise:
- qs<2,0>: 9 cases (seeds 1,2,3 x sizes 40,203,411) x 2 repetitions = 18 of 18 runs with 0 differing bytes between vendor and rewrite and between repetitions. qs<3,0> (`attn_qs_c_3_0.json`): 18 of 18.
- Controls (qs<2,0>, seed 1, N=203): pattern model without the column parity term: 8,893 bytes differ; pattern base 0x3f80 changed to 0x3f81: 16,709 bytes differ.
The rewrite models this in `qs_full`: `if (A & 2) vb[k] = pattern[(8*(col&1)+k)&15]`, and the global V load is skipped (`!(A & 2)`) because the listing has none. Without priming the rewrite matches nothing, as the vendor matches nothing. These are conditional results: compare.py cannot prime, so there is no table row. Harness need: a spec field such as `"prime": {"lds_halfword": "0x3f80+8*(i&15)", "blocks": 1000}` that launches a priming kernel with the vendor's LDS size before the kernel on both sides.
`attn_qs_c_3_0.json` uses N+700 rows (k, v, tbl range, kernarg 60) because it is g18b's `attn_qs_1_0.json` with the kernel changed: probe 1 masks the K row index with `v_and 0x1ff` instead of clamping to m-1, so rows up to 511 are read and the buffers must hold at least 512 rows even at N=40. That keeps every read in bounds; it is a requirement of the probe, not a range widened to pass. `attn_qs_c_2_0.json` uses the clamp, so it keeps N+8.

## Weak controls (g18b)

All reruns use the corrected rewrite; rows in `g18c-negctl.md` are named `<spec>__<control>.json`.

1. bt2<4,0> control "p to p+0.5" stayed MATCH in g18b. Rerun with the edit on the probe-4 line (`p = valid ? s + 0.5f : 0.0f`): MISMATCH 4 of 4 (18,425 of 18,560 elements differ). g18b's edit was most likely applied outside that line (their sed is not kept). The control script here refuses an edit that changes nothing.
2. Sentinel controls, two findings.
   a. The listing has no `-1e29` constant (0xefa18f08) in bt4, bt4x, bt2w, bt2<0,1/3/7/9/11> (count per kernel, grep of the full listing); those kernels compute alpha = expf(mo - mn) with no validity test and p = expf(sm - mn) with no mask (bt4 0x1d2000 tile body: `v_sub_f32 v94, v94, v128` then exp; masked lanes `v_cndmask 0xf149f2ca`). g18b's rewrite used the bt2<0,0> style there, so on `_mid` and `_low` it was wrong: baseline `attn_qs_c_bt4_0_mid`, `bt4_0_low`, `bt4x_0_mid`, `bt4x_0_low` MISMATCHed (vendor finite, rewrite NaN) with the g18b rewrite. Fixed with template parameter `ST` in `qs_bt_body` (ST=1 for bt4, bt4x, bt2w, bt2<0,1/3/7/9/11>; ST=0 for bt, bt2<0,0>,<0,2>,<1,0>,<2,0>,<8,0>,<16,0>,<32,0>,<64,0>). All of them MATCH on `_mid` and `_low` now. g18b's n2 on bt4/bt4x stayed MATCH because the constant is not in those kernels (control rows MATCH, expected). New controls pin style B: b1_alpha (restore the validity test) MISMATCH on bt4, bt4x, bt2w<7,7> `_mid` (12 of 12); b2_pmask (mask p) MISMATCH on bt4 `_low` and bt2<0,1> `_low` (8 of 8).
   b. n3 (running max init -1e30 to -1.7e38) on qs<0,0> `_low` stayed MATCH in g18b and no output can detect it: when the init matters every score is below -1e30, so every wave max is below -1e29, and the merge weight is `(m > -1e29) ? expf : 0` (qs_epilogue, @176DB4) = 0 for every wave, giving 0/0 = NaN with or without the change. New specs `0_0_low16`, `0_0_low16c`, `0_1_low16c`: 16 of 16 control rows MATCH, as predicted. For the paged kernels n3 is reachable only when the last tile is full: a partial last tile masks lanes to -1e30, the tile max becomes -1e30, and baseline and control both give NaN. New specs `_low16` (grid x = 1, `sel = 4*(N//4)+3`, `nblk = (N//16)*4` so nk is a multiple of 16; q,k random as in `_low`) and `_low16c` (same with K constant -2^50, exact in bf16). n3 results: bt2<0,0> and bt: MISMATCH 4 of 4 on `_low16c`, but only 2 of 4 on random `_low16` (N=40 detects, N=203 does not: with 12 tiles and scores spread over 20% of 1e30 the last tile rarely holds the running max, so exp underflows in both); bt4 and bt4x: MISMATCH on both. The constant-K spec is degenerate on purpose (all scores in a row equal, softmax uniform): it is an extra spec, needed only to reach the -1e30 init at large N. Every instance keeps non-degenerate specs (main, `_edge`, `_ext`, `_mid`, `_low`, `_low16`).

n2 (`-1e29` to `-3.4e38`) on `_mid`: MISMATCH on bt2<0,0>, bt, qs<0,0>, qs<0,1> (16 of 16); MATCH on bt4, bt4x (constant absent, 8 of 8).

## Fill choices
- main specs: random in the ranges g18b used (non-degenerate).
- `_mid` and `_low`: g18b's large magnitudes, kept: they exist to put scores near -1e29 and below -1e30.
- `_low16`: random K as `_low`. `_low16c`: constant K = -2^50, only to reach n3 at N=203 (reason above); one-token grid so that len%4 == 0 holds for the token that exists.
- flat qs_bt `_low16*` sets kernarg n=1 (offset 48) because that kernel uses one wave per token.
