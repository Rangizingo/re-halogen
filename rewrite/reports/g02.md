## How the listings were read

The checked-in `kernels-disasm/codeobj_53000.s` was made with llvm-objdump 21, which prints many VOP3 instructions as `.long`
(compares with 64-bit operands, shifts, some v_cmpx), so branch and index logic cannot be read from it alone. Ai-core has a newer
ROCm llvm-objdump (AMD LLVM 23.0.0git, under the `_rocm_sdk_core` python package of a podman overlay, used read-only) that decodes
all of them. Control flow and index math were read from that output; every line cite in the .hip headers is a `codeobj_53000.s:<line>`
of the checked-in listing, found by instruction address, or says ".long pair" / names the address when the checked-in listing cannot show it.

## What each kernel does (details and cites in the .hip headers)

- `k_deq_q8s32(src, dst, a, b, c)`: grid-stride loop over b blocks of 32 int8 plus one f16 scale; row = i / a, row stride pad16(K + K/16),
  scales at byte K of the row; out = bf16_rne(int8 * scale), K = c.
- `k_deq_q8g64`: same loop, 64 uint8 per block, one (scale, offset) f16 pair per block, row stride K + K/16 unpadded;
  out = bf16_rne(fma(u8, scale, offset)) with one rounding (v_fma_mix_f32).
- `k_lq8s32<M,R,W,F32>(W, x, y, K, N)`: GEMV of N rows by M tokens. 256 threads, R lanes per row, W waves per row, rows per block 256/(R*W).
  Weights decode to bf16 first (RNE, no NaN special case), then a v_dot2_f32_bf16 chain of 8 per 16-weight group, xor-butterfly over the R lanes,
  and for W>1 an LDS sum over waves in wave order starting from +0.0. F32=true stores the f32 sum instead of bf16.
- `k_lq8w<M,R,W>`: same shape with the q8g64 decode (row stride K + K/16, (scale, offset) pair per 64 weights).
- `k_lq8w_grp<M,32,2>(LqGrp, x, K)`: up to four members in one launch (block ranges picked from the member start blocks), shape picked at run
  time from the member row count (N < 9: 8 waves per row, otherwise 2 waves, 4 rows), then one of six epilogues (bf16, silu, sigmoid, f32 2*sigmoid,
  f32 sigmoid, two-plane bf16 store). LqGrp layout reconstructed from the loads (0x48 bytes per member, count at +0x120).

## Tolerance

All rows are bitwise (compare.py prints `tol=bitwise`). Nothing needed a tolerance: the vendor reduction orders, the fma_mix single
rounding, the IEEE division and v_exp_f32 on `v * -1.442695` were all reproducible instruction for instruction.

## Spec design

- Free size N = rows (ragged sizes 77 and 1003; the lq8w_grp b-variant uses 512 and 1536 plus 600/1003 at M=1, see caveat below).
  Seeds 1, 2, 3. K = 2336 (q8s32, 146 groups) and 2368 (q8g64, 148 groups): not a multiple of the 256-lane step, so the tail handling is exercised.
- Weight buffers are filled as f16 random in [-1, 1] over the whole row buffer: the int8/uint8 region gets those bytes, and the scale region gets
  finite sane scales. `_u8` specs fill everything with uniform random bytes (scales include inf and NaN) and still match bitwise.
- `_k96` / `_k192` specs: K = 96 / 192 (6 / 12 groups, fewer groups than lanes, W=8 leaves waves with no work).
- `deq_*_loop` specs launch about a quarter of the blocks so the grid-stride loop runs several times. `deq_*_exh` specs put every f16 bit pattern
  through the scale (and for q8g64 through the offset) in one launch: one row of 65536 blocks, buffer filled with `iota`.
- Output buffers carry 64 sentinel elements past the end (const -99); compare.py compares them, so out-of-range writes show up.
- compare.py's UNTOUCHED check requires every dumped output to be written by both kernels; the lq8w_grp specs size their members so each dumped
  buffer is written (plane 1 of mode 5 only with N >= 257).
- lq8w_grp spec a: members (N, mode) = (N,1) (5,2) (N+3,3) (8,0); spec b: (N,5 with both planes) (9,4) (12,1) (1,0). Together all six modes, both
  shapes (N<9 and N>=9) and the N=8/9 boundary are covered, for every M = 1..8.

## Caveats and things not covered

- lq8w_grp mode 5 with M > 1 writes token m at plane + m*(N/2)*2 + base + idx*2. That layout only has disjoint token slices when N is a multiple of 512
  (the real use); with N = 600 the slices overlap, the writes race, and vendor vs rewrite differ run to run. The first sweep showed exactly that
  (M >= 2, N = 600); spec b therefore runs M >= 2 at N = 512 and 1536. M = 1 is also run at 600 and 1003 and matches.
- lq8w_grp: only `count = 4` is tested (member selection with fewer members is read from the listing, not run). Member bytes +0x18..+0x2f
  are not read by the kernel in any listing checked (m=1,2,3,8 `s_load` offsets) and are left zero. Modes >= 6 are not exercised (the listing falls
  into the plain bf16 store; the rewrite does the same via `default:`).
- The per-token LDS layout for M > 1 is read from the M=2 listing for lq8w_grp (t/M, t%M, stride M*4 per wave); for lq8s32 and lq8w it is inferred and
  confirmed only by the bitwise match for M = 2..8.
- The token stride of x is K elements for all instances (read from E:595755 for lq8s32<2,16,1>, inferred and matched for the rest).
- Wave size is 32 (kernargs.json `wavefront_size`); the rewrites use `__shfl_xor` with width R, compiled to ds_bpermute like the vendor.
- Hook note: `ftr-artifact-gate` refused me a scratch `.py` file in the scratchpad (outside the repo); I did the report-row aggregation with awk instead. No hook was bypassed.
- Output location: the harness refused writes to the main checkout from this worktree session, so every file listed here is in the worktree
  `/Users/peterb/.claude/worktrees/agent-a429c303d9bcc431c/rewrite/`; the table files were copied from Ai-core into it.
