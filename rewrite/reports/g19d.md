## Verdicts

- P5: defined, no caveat. The k*e table is zero-filled by the kernel's own prologue; A = 0 is what the vendor computes.
- P8: defined, no caveat. v10..v13 are computed as 0.125 times small integers; the rewrite now computes them that way.

g19b's claims "P5 reads LDS the kernel never writes" and "P8 reads VGPRs never written" were artifacts of the old listing (`.long` hid the instructions). Both caveats are withdrawn.

## P5 (`k_dnc_scan3w<2,4,true,false,5>`)

What it stores at 0x2800, when, which lanes (all in the prologue, before the first barrier):
- 176798-176823: a loop with `s8 = 0, 2, 4, 6, 8` (176802 `s_add_i32 s8, s8, 2`, 176804 `v_cmp_eq_u32 s9, s8, 10`, exit when s8 == 10).
- 176815 `v_mov_b16 v2.l, 0`, 176816 `ds_store_b16 v3, v2 offset:10240` (10240 = 0x2800); v3 = 2*(s8*128 + tid) (176809 `v_lshl_or_b32 v1, s8, 7, v0`; 176814 `v_lshlrev_b32 v3, 1, v1`). Value: 0. Guard: `v_cmpx_le_u32 s24, 9` at 176813 with s24 = s8 | 0.
- 176821 `v_mov_b16 v1.l, 0`, 176822 `ds_store_b16 v2, v1 offset:10496` (0x2900 = 0x2800 + 256 B = one 128-halfword row): the second row (s8 + 1), same 128 lanes (all 128 threads, one halfword each). Guard: `s_and_saveexec_b32 s11, s9` at 176818 with s9 = (s25 <= 9).
- Total: 10 rows x 128 halfwords = 2560 B = [0x2800, 0x3200). The table is 16 rows x 160 B (`v_mad_u32_u24 v84, 0xa0, v2, s4` at 176877, s4 = 0x2800, v2 = lane & 15), so the whole table is covered. The next region (state S) starts at 0x3200 (176745 `v_mad_u32_u24 v1, v75, s7, 0x3200`).
- Ordering: the loop exits, then `s_barrier` at 176828 (and 176897, 176899 again before stage 1), then `ds_load_b128 v[17:20], v84` ... at 176901 and later, `v_wmma_f32_16x16x16_f16 v[99:106], v[17:24], v[33:40], v[9:16]` at 176937. So every read of the table is after the barrier that follows the stores.
- Nothing else writes the table: the only other `ds_store` forms in the kernel are `ds_store_b32 v7` (176789, S, base 0x3200+), `ds_store_b32 v77` (177413, g array at 0xb600+), 32 `ds_store_b16 v88` with offsets 0..7708 (vn, max end 10208 < 10240) and `ds_store_2addr_b32 v85` (S). There is no `ds_store ... offset:10240` after the prologue, which is what P5 removed relative to P0 (P0 stores k*e there each tile and has the same prologue zero fill, which only matters for P0's unused rows; labeled inferred, P0 not re-read here).
- Why A = 0 reproduces it: the A operand of the stage-3 WMMA is this zeroed table, so WMMA(0, B, acc) = acc (adding +0 products). g19b's rewrite used `a[j] = 0` directly, which is the same value.
- Rewrite (vendor's way): `k_probe_d_p5` allocates `__shared__ f16 ke[16*80]`, zero-fills it in the prologue before the first `__syncthreads`, and stage 3 reads `a[j] = ke[lr*80 + tl]`; the k*e computation does not reach the WMMA.
- Runtime cross-check with priming (supporting, not the proof): `dnc_scan3w_probe_d_p5_primed.json` launches `dnc_scan3w_probe_d_prime.hip` (every halfword of 46848 B LDS := 0x3c00 = 1.0) before both the vendor and the rewrite. 6 of 6 MATCH (seeds 1,2,3 x N = 128, 100), rows carry `primed`. If the vendor read leftover LDS, 1.0 values would reach the WMMA and the output would diverge (the unprimed control with a 1.0 table, below, differs in 1,178,837 elements). The priming mechanism is the one proven to change vendor output in g18d; it is not re-proven on this kernel.

## P8 (`k_dnc_scan3w<2,4,true,false,8>`)

- 188337 `v_pk_mul_f16 v11, 0x3000, v5 op_sel_hi:[0,1]`, 188341 v13 from v4, 188359 v10 from v2, 188372 v12 from v3. 0x3000 is f16 0.125. v14..v17 copy v10..v13 (188342 `v_mov v15, v11`, 188346 `v_mov v17, v13`, 188364 `v_mov v14, v10`, v16 from v12 by dual mov), so the A operand halves repeat.
- v2..v5 are packed f16 integers (188315-188336): `v_and_b32 7`, `v_cvt_f32_ubyte0`, `v_xor_b32 4`, `v_cvt_f16_f32` into .l/.h. Decoded with t = tid: v2 = [t&7, (t+1)&7], v5 = [(t+2)&7, (t+3)&7], v3 = [(t+4)&7, (t+5)&7] (188334 xor 4 for the low half, 188368 `v_cvt_f16_f32 v3.h` from (t+5)&7), v4 = [(t+6)&7, (t+7)&7].
- So A[m][k] = 0.125 * ((m + (k & 7)) & 7), m = lane & 7 (= lr & 7 for lr = lane & 15), k = 0..15 with the second half repeating the first. This is g19b's measured table, now read from the listing.
- Rewrite: `p8_a(lr, j)` = `(f16)n * (f16)0.125` with n = (lr + (j & 7)) & 7, an f16 multiply as the vendor does. Exact (n/8), so bitwise equal to g19b's float form; the point is the operand is computed from data as the vendor computes it, and nothing was read from hardware to derive it.
