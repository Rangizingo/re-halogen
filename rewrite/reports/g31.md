## Method
- `trace`: for every gap, the exact dataflow chain the audit followed to call the value a bound (listing line of each step).
- Every bound turned out to be one of: a compile-time loop trip count, a loop step, an address, a launch-size guard that is always true, or a token-versus-k guard.
- A compile-time count cannot be reached by one input and not another. If it were wrong in a way that matters, the random-operand bitwise MATCH rows (tables g16, g16b, g09, g19, g10, g20) would fail; none fail on these bounds. Reasoning is at loop-kind level, not per use (about 900 uses).
- The only input-dependent bounds are the scan3x_b token guards. Reaching run: existing specs, `--sizes 18,19,22,23,34,35,38,39,42,43,46,47,50,51,54,55,58,59 --seeds 1,2` (k straddles every gap constant c: k=c and k=c+1), 10 instances, 360 rows, all bitwise MATCH, rows in `rewrite/tables/g31.md`. The old specs only used N=100,128, which never sat on those constants.
