## Arithmetic (what the rewrite does; every item verified against the vendor)

- Weight row: K/2 bytes, byte i holds k=2i (low nibble) and 2i+1 (high nibble); row r = expert*ROWS + channel (ROWS 2560 for B2, 1280 for B0).
  B0 up rows are gate rows + 640 (`v_cndmask 0x280` on the lane half, listing i1002 FBD6C4-FBD6F0).
- A=1 decode: bf16_rne(float(f16 scale) * lut[nibble]) (v_fma_mix_f32 with an inline -0 addend is a plain f32 product; RNE is
  `v + ((v>>16)&1) + 0x7fff` with no NaN case; the table lookup is a v_perm/v_bfi byte-table select). A=2 decode: f16(lut) via
  s_cvt_f16_f32 (RNE) then v_pk_mul_f16 by the f16 scale.
- Scale groups: E=2, E=1 use one f16 per 128 k at `base+soff+row*stride+2c` (stride 10 B for K=640, 40 B for K=2560). E=0 uses one f16
  per 32 k (global_load_b64 loads four at a time, `offset:8` for the next four): entry 4c+q for the k16 pair 2q,2q+1 of chunk c
  (stride 40 B for K=640, 160 B for K=2560). Found with a one-hot probe (effective scale per k with scales 1..5), then confirmed by MATCH.
- GEMM: per wave two A tiles (16 channels each) by NT token tiles of 16; `v_wmma` D = A(weights) x B(x), accumulators never cleared between
  chunks; per chunk the eight k16 blocks run in ascending order for every accumulator (ds_load offsets 0,32,..,224 per accumulator,
  checked in the E=2 listing). Fragment slot f of block j holds k = 16j + 8(f/8) + {0,2,4,6,1,3,5,7}[f%8] on both operands (x is stored
  to LDS as e0,e2,e4,e6,e1,e3,e5,e7 per 8; the weight register order low-nibbles-then-high-nibbles gives the same permutation). The
  rewrite calls the same WMMA intrinsic with the same operand bits, so the in-instruction summation order is the hardware's own.
- x rows: token n of a tile reads row `start + min(n, nrows-1)` (B0 through idx / 10; the signed division is mulhi 0x66666667 then `>>2`,
  which is /10 not /5; a first attempt with /5 gave a clean 100% mismatch outside token 0 and a one-hot probe found the 10).
- D layout (gfx11 w32): lane l, vgpr i = D[row 2i + (l>>4)][col l&15]; row = channel in the tile, col = token in the tile.
- Epilogues:
  - B2 E=2 and B2 E=0: y = bf16_rne(acc).
  - B0 E=0: g = bf16(acc_gate), u = bf16(acc_up) widened to f32; y = bf16_rne(u * (g / (1 + exp2(g * -1.4426950f)))); the division is the
    IEEE sequence (div_scale, rcp, fma chain, div_fmas, div_fixup); same formula as exp_gu in g05.
  - B2 E=1: accs go through LDS, then per token and per 128-channel group a 128-point Walsh-Hadamard transform, scaled by the float with
    bits 0x3db504f3 (1/sqrt(128)), multiplied by svh[c] (f16), bf16_rne. Butterfly order (listing i1212e1, 0x...E24E74-E25230): in-register
    stage on the lane's four channels (a+b, a-b, c+d, c-d, then sums/differences of those), then lane bits 0..3 (DPP row_xmask 1,2,4,8), then
    lane bit 4 (permlanex16); a stage gives the even partner `x + p` and the odd partner `p + (-x)`.
  - B0 E=1: gate and up each go through that WHT (times 0x3db504f3, then times svh_g / svh_u), P = u * silu(g), then the first stage of a
    second WHT is fused with suh: with b1 = round(P1*suh1), b3 = round(P3*suh3): x0 = fma(P0,suh0,b1), x1 = fma(P0,suh0,-b1),
    x2 = fma(P2,suh2,b3), x3 = fma(P2,suh2,-b3), then (x0+x2, x1+x3, x0-x2, x1-x3) and the remaining lane stages, times 0x3db504f3,
    bf16_rne (listing i1011, E05A74-E05F..).

## Listing decode problem (read this before reusing the listings)

kernels-disasm/codeobj_53000.s prints 235 words of the smallest instance as `.long` and then mis-decodes the following dwords as separate
instructions (v_mul_lo_u32, v_add_co_u32, v_lshlrev_b64, v_cmp_*_e64 with an unusual src2 field, and 16-bit moves). The same happens in
every q4moe instance. Method used here: slice the kernel from the listing's raw words, clear the src2 field of the VOP3 words llvm-mc rejects, re-disassemble with
`llvm-mc --disassemble -triple=amdgcn-amd-amdhsa -mcpu=gfx1151` (Ai-core, LLVM 21.1.8), and decode the remaining 4-byte VOP1 words
(0x7e../0x7f.., opcode 0x1c) as `v_mov_b16` with true16 half selects. The `UNDEC cc10....` pairs in the A=2 listings are VOP3P `v_pk_mul_f16`
(scale applied to two packed f16 weights). The scratch scripts are not in the repo (scratch only).

## Findings worth a follow-up

- E (the last template arg) is not a scheduling knob: it selects the scale granularity (E=0 per 32 k) and the epilogue (E=1 adds the Hadamard
  folds and reads svh/suh; E=2 and E=0 on B2 are plain stores). The host fill of slot 0x60 for E=1 and 0x68/0x78 is in
  analysis/closure/expert-dispatch-r5b.md section 3.
- B=0 reads x through idx/10: idx holds slot ids and /10 gives the activation row (inferred: ten slots per token).
- 1/sqrt(128) in the vendor is the float with bits 0x3db504f3. The decimal literal 0.08838835f rounds to 0x3db504f4 and changed 1 of 67584 outputs in the first try (E=1 down).
- NaN sign is not reproduced for E=1 when a whole 128-group is NaN: vendor gives +qNaN (0x7fc0) for half of the outputs, the rewrite gives -qNaN (0xffc0) (every element was NaN in that run: an LUT of +-7e4 overflows f16 to inf). The edge spec was
  then rebuilt without overflow (LUT 6e4, scales +-0.9). Finite inputs match bitwise; inf/NaN inputs to E=1 are unproven.
- A=2 saturates x: v_cvt_pk_rtz_f16_f32 gives 65504 for |x| > 65504 where RNE would give inf; the edge specs exercise it (negative control N5).

## Remaining risks

- E=1 with NaN/inf inside a 128-group: vendor and rewrite give different NaN signs (see findings). Finite data matches.
- `idx` meaning (ten slots per token, so /10 gives the token) is inferred from the divisor, not from a consumer.
- Item fields outside the tested ranges (nrows 0, nrows above TILE, k above 9 (B2) or 4 (B0), more than 4 experts, a count larger than the item array) are untested; the vendor
  `v_min_i32 nrows-1` with nrows = 0 would read slot start-1.
- Main specs use f16-random bytes (nibbles not uniform); `_uni` uses seeded uniform bytes; LUTs are one fixed NF4-like table plus the edge table.
