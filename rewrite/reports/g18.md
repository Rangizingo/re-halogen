## attn_qs: why BLOCKED, and what a follow-up needs

Reconnaissance only (work/kernels slices, e.g. `*9k_attn_qsILi4ELi0*`, 997 filtered lines for the smallest; the 33 listed variants run 1000 to 5200 lines each, 81k lines total):
- Kernel args: 12 (qs: q/k/v bf16 pointers, i64 stride, pointer, out, `PKi` x3 index arrays, 3 ints). The first lines read `lens[0] + blockIdx.x`, a per-sequence length from a `PKi` array and a row table (listing `9k_attn_qsILi4ELi0` lines 3-66), i.e. paged/batched decode with a block table. Nothing in analysis/ documents the host-side meaning of these arrays (grep of analysis/closure for attn_qs finds only a count in kernel-binding.md:50), so a spec needs those semantics recovered first.
- 64 KB LDS (qs<a,0>), 16-32 WMMA, 100+ live VGPR arrays, 0xf149f2ca (about -1e30) running-max init at line 82.
- The vis_attn_w work shows the method that works: read the kernel structure, write the logical algorithm with explicit WMMA builtins, let MATCH rows settle inferred details (lane layouts, bf16 truncation points). The same needs doing per qs variant (template args a in {1,2,3,4,8,16,32,64}, b in {0,1,2,3,6,7,8,9,11} are unknown flags).
- Recommended order: k_attn_qs<4,0> (smallest), then bt4 (4 variants, ~1500 lines), then qs<a,0>, bt2/bt2w, qs_bt (5200 lines, last).
