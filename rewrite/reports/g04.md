## What each family does (details and cites are in the .hip headers)

- bf16: `y[i] = x[i] << 16`, 64-bit global index with guard (:18564-18586).
- linear / linear_f32: one block per (a row x, b row y) dot product; strided fma loop, LDS tree from blockDim/2, thread 0 stores `c[y*gridDim.x + x]` (bf16 RNE or f32). 256 threads (:18370-18515, :18590-18739).
- linear_m<M> / linear_f32_m<8>: M rows of `a` against one `b` row, M accumulators, one LDS slot of 256 floats each, per-slot tree, threads t < M store `c[y*ldc + x*M + t]` (:853917-854121).
- linear_mt<8,T,256>: 8 rows x T tokens, 8*T accumulators; T passes of an 8-slot tree (LDS 8192 B); token k stored at `c[k*ldc + x*8 + t]` (:834978-835693).
- lbfw<M,U>: wave32 per output row, 8 rows per 256-thread block, 16 B per lane per vector, U vectors per step (U*256 elements), `v_dot2_f32_bf16` chain (`__builtin_amdgcn_fdot2_f32_bf16`), xor-shuffle butterfly 16,8,4,2,1, lane 0 stores bf16 RNE `Y[m*N + r]` (:141666-146699). Requires K to be a multiple of U*256 (the vendor has no tail; specs use K=2048).
- lbfw_lds<M,4>: same math with X staged to LDS first (block-wide 16 B copies, barrier) (:141223-141665). LDS holds M*K bf16, so K <= 6144.
- linear_f32_q4 family: weight buffer `q` is a 64 B table of 16 f32, then 4-bit codes (row stride K/2 bytes, low nibble for even i), then f16 scales (one per 32 elements, row stride is a kernarg). Dequant is `w = bf16_rne(f16 scale * lut[code])` widened to f32, then `acc = fma(bf(x), w, acc)` (:19004-19045, :946537-946553). `_m<8,U>`: U (1,2,4,8) is only a loop unroll; the accumulator chains are the same single chains in increasing i (inferred from 8 accumulators in all U, confirmed by MATCH). `_mt<8,T,4,256>`: T tokens at `x + k*K`, 4 is the unroll, 256 the block.

## Findings worth a follow-up

1. Products of two bf16 values are exact in f32 (8+8 mantissa bits), so fma versus mul+add cannot be separated by these kernels. The first linear_m negative control (mul+add) printed MATCH for that reason (and the compiler contracts it anyway); it was replaced with an accumulator-init change and the table was regenerated clean. Only rounding, reduction order and index math are detectable here.
2. k_linear and the lbfw kernels do not guard the tail of K (lbfw loads run past K). Specs only use K that the vendor handles.
3. linear_mt and q4_mt have no row guard: grid must be exactly ceil(rows/8).
4. The `.long` words hide VOP3 ops: v_lshlrev_b64 / v_lshrrev_b64 / v_add_co_u32 / v_cmp_*_i64. If a later agent needs exact decode, llvm-objdump with a newer LLVM or `--mcpu=gfx1151` plus `-M no-aliases` may print them; not tried.
5. The shared scratchpad `run.sh` was overwritten by me once by accident (same name as another agent's helper); it was restored by its owner. My helpers are prefixed `g04_`.
